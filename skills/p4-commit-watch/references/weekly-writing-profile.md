# 周报写作画像与迭代记录

## 当前画像（2026-08-10）

- 正文按版本线组织，如 `2.8.2`、`2.9`、`框架`；没有可靠版本归属时不强行分类。
- 每条使用“事项 + 进展/结果”的短句，不展开 API、类名、资源路径或实现过程。
- 保留玩法、系统或业务的具体名称，避免改写成“能力侧”“交互物侧”等泛称。
- 详细核对表按负责人保留事实归属与 `source_cls`，供人工回查；最终交付的“程序组本周工作汇报（简洁版）”不展示负责人。
- 简洁版先按版本线组织，再按玩法、系统或功能模块归并；同一模块的相关接入、优化和问题修复可以合并为一条短事项。
- 不同模块不得为了压缩篇幅合并，例如“战斗料理课”和“拍立得能力”必须分别成条；不能仅因同一负责人或同一版本而合并。
- 跨负责人合并只在简洁版中同一模块由多人共同推进、且每项事实都有来源 CL 时允许；详细核对表仍分别归属。
- 无 P4 来源的事项不得自动补写；可在“待补来源”中单列，等待人工确认。

## 不可突破的事实约束

- 每条候选归纳必须带 `source_cls`，并通过 `validate-weekly-attribution.py`。
- 成员名称以脚本的 P4 账号映射为唯一来源；台账中不得出现未映射的 P4 账号作为展示名。
- 生成候选稿前必须先产出成员—CL 台账；候选稿不得使用旧周报正文作为事实来源。
